# 代码重构技能

基于 Martin Fowler 的《重构：改善既有代码的设计》（第2版）的系统化代码重构方法。此技能强调由测试支持的安全、渐进式更改。

> "重构是在不改变代码外部行为的前提下，改善其内部结构的过程。" — Martin Fowler

## 核心原则

1. **行为保持**：外部行为必须保持不变
2. **小步前进**：进行微小的、可测试的更改
3. **测试驱动**：测试是安全网
4. **持续进行**：重构是持续的，不是一次性事件
5. **协作**：每个阶段需要用户批准

## 工作流程概览

```
阶段 1：研究与分析
    ↓
阶段 2：测试覆盖率评估
    ↓
阶段 3：代码异味识别
    ↓
阶段 4：重构计划创建
    ↓
阶段 5：渐进式实施
    ↓
阶段 6：审查与迭代
```

---

## 阶段 1：研究与分析

### 目标
- 理解代码库结构和目的
- 确定重构范围
- 收集业务需求的上下文

### 向用户提问
开始之前，澄清：

1. **范围**：哪些文件/模块/函数需要重构？
2. **目标**：你要解决什么问题？（可读性、性能、可维护性）
3. **约束**：是否有不应更改的区域？
4. **时间压力**：这是否阻塞了其他工作？
5. **测试状态**：是否存在测试？它们是否通过？

### 操作
- [ ] 阅读并理解目标代码
- [ ] 识别依赖项和集成
- [ ] 记录当前架构
- [ ] 注意任何现有的技术债务标记（TODO、FIXME）

### 输出
向用户展示发现：
- 代码结构摘要
- 已识别的问题区域
- 初步建议
- **请求批准继续**

## 阶段 2：测试覆盖率评估

### 为什么测试很重要
> "没有测试的重构就像不系安全带开车。" — Martin Fowler

测试是安全重构的**关键推动因素**。没有测试，你可能会引入 bug。

### 评估步骤

1. **检查现有测试**
   ```bash
   # Look for test files
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

2. **运行现有测试**
   ```bash
   # JavaScript/TypeScript
   npm test

   # Python
   pytest -v

   # Java
   mvn test
   ```

3. **检查覆盖率（如果可用）**
   ```bash
   # JavaScript
   npm run test:coverage

   # Python
   pytest --cov=.
   ```

### 决策点：询问用户

**如果测试存在且通过：**
- 继续到阶段 3

**如果测试缺失或不完整：**
提供选项：
1. 先编写测试（推荐）
2. 在重构过程中逐步添加测试
3. 在没有测试的情况下继续（有风险 - 需要用户确认）

**如果测试失败：**
- 停止。在重构之前修复失败的测试
- 询问用户：我们应该先修复测试吗？

### 测试编写指南（如需要）

对于每个被重构的函数，确保测试覆盖：
- 正常路径（正常操作）
- 边界情况（空输入、null、边界值）
- 错误场景（无效输入、异常）

使用"红-绿-重构"循环：
1. 编写失败的测试（红色）
2. 使其通过（绿色）
3. 重构

## 阶段 3：代码异味识别

### 什么是代码异味？
代码中更深层问题的症状。它们不是 bug，而是代码可以改进的指示器。

### 常见代码异味检查

详细目录请参见 [references/code-smells.md](references/code-smells.md)。

#### 快速参考

| 异味 | 迹象 | 影响 |
|-------|-------|--------|
| **过长方法** | 方法超过 30-50 行 | 难以理解、测试、维护 |
| **重复代码** | 相同逻辑在多处出现 | Bug 修复需要在多处进行 |
| **过大类** | 类有太多职责 | 违反单一职责原则 |
| **特性羡慕** | 方法过多使用另一个类的数据 | 封装不良 |
| **基本类型偏执** | 过度使用基本类型代替对象 | 缺失领域概念 |
| **过长参数列表** | 方法有 4+ 个参数 | 难以正确调用 |
| **数据泥团** | 相同数据项一起出现 | 缺失抽象 |
| **Switch 语句** | 复杂的 switch/if-else 链 | 难以扩展 |
| **投机性通用** | "以防万一"的代码 | 不必要的复杂性 |
| **死代码** | 未使用的代码 | 困惑，维护负担 |

### 分析步骤

1. **自动化分析**（如果脚本可用）
   ```bash
   python scripts/detect-smells.py <file>
   ```

2. **手动审查**
   - 系统地走查代码
   - 记录每个异味的位置和严重程度
   - 按影响分类（严重/高/中/低）

3. **优先排序**
   关注以下异味：
   - 阻塞当前开发
   - 导致 bug 或困惑
   - 影响最常更改的代码路径

### 输出：异味报告

向用户展示：
- 已识别异味列表及位置
- 每个异味的严重程度评估
- 建议的优先顺序
- **请求批准优先级**

## 阶段 4：重构计划创建

### 选择重构手法

对于每个异味，从目录中选择适当的重构手法。

详细列表请参见 [references/refactoring-catalog.md](references/refactoring-catalog.md)。

#### 异味到重构的映射

| 代码异味 | 推荐的重构手法 |
|------------|---------------------------|
| 过长方法 | 提炼方法、以查询取代临时变量 |
| 重复代码 | 提炼方法、上移方法、塑造模板方法 |
| 过大类 | 提炼类、提炼子类 |
| 特性羡慕 | 搬移方法、搬移字段 |
| 基本类型偏执 | 以对象取代基本类型、以类取代类型码 |
| 过长参数列表 | 引入参数对象、保持对象完整 |
| 数据泥团 | 提炼类、引入参数对象 |
| Switch 语句 | 以多态取代条件表达式 |
| 投机性通用 | 折叠继承体系、内联类、移除死代码 |
| 死代码 | 移除死代码 |

### 计划结构

使用 [templates/refactoring-plan.md](templates/refactoring-plan.md) 中的模板。

对于每个重构：
1. **目标**：什么代码会更改
2. **异味**：解决什么问题
3. **重构**：应用哪种技术
4. **步骤**：详细的微步骤
5. **风险**：可能出什么问题
6. **回滚**：如需要如何撤销

### 分阶段方法

**关键**：逐步分阶段引入重构。

**阶段 A：快速收益**（低风险，高价值）
- 重命名变量以提高清晰度
- 提取明显的重复代码
- 移除死代码

**阶段 B：结构改进**（中等风险）
- 从长函数中提取方法
- 引入参数对象
- 将方法移至适当的类

**阶段 C：架构更改**（较高风险）
- 用多态替换条件表达式
- 提炼类
- 引入设计模式

### 决策点：向用户展示计划

在实施之前：
- 展示完整的重构计划
- 解释每个阶段及其风险
- 获得每个阶段的明确批准
- **询问**："我应该继续阶段 A 吗？"

## 阶段 5：渐进式实施

### 黄金法则
> "更改 → 测试 → 绿色？ → 提交 → 下一步"

### 实施节奏

对于每个重构步骤：

1. **预检查**
   - 测试通过（绿色）
   - 代码编译

2. **进行一个小更改**
   - 按照目录中的机制操作
   - 保持更改最小

3. **验证**
   - 立即运行测试
   - 检查编译错误

4. **如果测试通过（绿色）**
   - 使用描述性消息提交
   - 进入下一步

5. **如果测试失败（红色）**
   - 立即停止
   - 撤销更改
   - 分析出了什么问题
   - 如不清楚则询问用户

### 提交策略

每个提交应该是：
- **原子的**：一个逻辑更改
- **可逆的**：容易回退
- **描述性的**：清晰的提交消息

示例提交消息：
```
refactor: Extract calculateTotal() from processOrder()
refactor: Rename 'x' to 'customerCount' for clarity
refactor: Remove unused validateOldFormat() method
```

### 进度报告

在每个子阶段之后，向用户报告：
- 所做的更改
- 测试是否仍然通过？
- 遇到的任何问题
- **询问**："继续下一批？"

## 阶段 6：审查与迭代

### 重构后检查清单

- [ ] 所有测试通过
- [ ] 没有新的警告/错误
- [ ] 代码编译成功
- [ ] 行为未变（手动验证）
- [ ] 如需要已更新文档
- [ ] 提交历史整洁

### 指标比较

运行前后复杂度分析：
```bash
python scripts/analyze-complexity.py <file>
```

展示改进：
- 代码行数变化
- 圈复杂度变化
- 可维护性指数变化

### 用户审查

展示最终结果：
- 所有更改摘要
- 前后代码对比
- 指标改进
- 剩余技术债务
- **询问**："你对这些更改满意吗？"

### 后续步骤

与用户讨论：
- 要解决的额外异味？
- 安排后续重构？
- 在其他地方应用类似更改？

## 重要指南

### 何时停止并询问

在以下情况下始终暂停并咨询用户：
- 对业务逻辑不确定
- 更改可能影响外部 API
- 测试覆盖率不足
- 需要重大架构决策
- 风险级别增加
- 遇到意外的复杂性

### 安全规则

1. **永远不要在没有测试的情况下重构**（除非用户明确确认风险）
2. **永远不要进行大的更改** - 分解为微小步骤
3. **永远不要跳过测试运行** - 每次更改后都要运行
4. **永远不要在测试失败时继续** - 先修复或回滚
5. **永远不要假设** - 有疑问时就问

### 不要做什么

- 不要将重构与功能添加混合
- 不要在生产紧急情况下重构
- 不要重构你不理解的代码
- 不要过度工程化 - 保持简单
- 不要一次重构所有内容

## 快速入门示例

### 场景：带有重复的过长方法

**之前：**
```javascript
function processOrder(order) {
  // 150 lines of code with:
  // - Duplicated validation logic
  // - Inline calculations
  // - Mixed responsibilities
}
```

**重构步骤：**

1. **确保测试存在** - 为 processOrder() 编写测试
2. **提取**验证逻辑到 validateOrder()
3. **测试** - 应该通过
4. **提取**计算到 calculateOrderTotal()
5. **测试** - 应该通过
6. **提取**通知到 notifyCustomer()
7. **测试** - 应该通过
8. **审查** - processOrder() 现在编排 3 个清晰的函数

**之后：**
```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```
